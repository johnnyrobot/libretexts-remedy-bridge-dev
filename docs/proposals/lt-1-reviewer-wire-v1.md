# LT-1 reviewer wire v1 — proposal revision r2

**Status: approved contract r2 with the 2026-10-29 Chief implementation addendum.** The approved immutable source is `a67d9d8b7efd9189f76885ecbd6394a9f3d92f54`, corpus `lt1-wire-v1-r2`. ## Approved additive clarifications

Preview, revise-preview and restore-preview responses expose authoritative `review_expires_at` as integer Unix seconds alongside the exact `review_binding`. Conductor stores both and caps assertion expiry at `min(iat + 60, review_expires_at, key-not-after)`; expired/too-short previews require fresh review. Expiry is outside the signed binding.

`stale_preview` and `target_mismatch` always return `evidence_effect:invalidate`, including `not_attempted` outcomes. A matched, confirmed `no_change` preserves evidence; `pending` holds it; actual or unknown mutation invalidates it. None of these outcomes replaces a fresh scan.

Authenticated `GET /readyz` returns 200 only when the configured capabilities are ready, otherwise 503, with `{ok:boolean,state:ready|degraded|misconfigured,capabilities:{scan:boolean,preview:boolean,mutate:boolean,operation_status:boolean}}` and an optional fixed safe error code. It requires the hop service key and reveals no key IDs, paths or values. Public `GET /healthz` returns sanitized liveness only. Server uses private readiness and deployment preflight checks the capabilities needed by its enabled profile. No public panel/exposure change is approved.

Implementation is delivered in focused slices. The first adds native verification/authentication and deliberately reports signed mutation/status unavailable until the durable writer slice is installed. Required mode never falls back to local mutation handlers.

## Ownership and trust

Conductor verifies its user JWT and current project mutation permission, resolves the project's **stored** canonical CXone target, and obtains a preview from the configured Remedy service. It stores the preview token, binding, and reviewed diff against that user/project/session; browser-supplied target, binding, subject, or assertion never override those records. At explicit confirmation it rechecks permission, project target, current review identity, and expiry, then signs exactly that stored preview binding. A changed target, tier, mode, output, or snapshot invalidates review and requires a new preview and confirmation. An auditor/foreign-project user cannot obtain a mutation assertion. `sub` is the immutable verified Conductor user ID, not an email/display name or a request field.

Service authentication is exact:

| Hop | Credential and transport | Required behavior |
|---|---|---|
| Conductor → Remedy Server | Existing `APP_API_KEY` supplied as `X-API-Key`; TLS whenever off-host. | Reuse the existing configured application key policy, reject missing/incorrect/duplicate credential headers, never forward this header to Bridge. Do not put it in a browser or log. |
| Remedy Server → Bridge | `X-Remedy-Service-Key`, loaded from `REMEDY_BRIDGE_SERVICE_KEY_FILE` at **both** ends. | File contains exactly 64 lowercase hex characters (32 random bytes), optionally one terminal LF, with no other whitespace. Parse once at startup; absent/malformed/unreadable key fails required-mode startup. Header must be exactly the 64 characters, single occurrence. Compare decoded equal-length byte buffers with native constant-time comparison. Never expose it to browser code, query strings, assertion claims, logs, responses or snapshots. No network key discovery. |

For existing variable-length application keys use constant-time comparison of fixed-length SHA-256 digests, not ordinary string equality; Bridge's fixed-format service key uses `timingSafeEqual`. An invalid format is rejected before comparison. Header names are HTTP case-insensitive; duplicates must be detected before framework coalescing. A credential accepted on one hop is not automatically valid on the other. TLS/service authentication and reviewer signatures are separate requirements; no assertion substitutes for a service credential.

In required-signature mode **every sensitive read, scan, snapshot listing, image description, preview/revision, operation-status request and every mutation alias** requires service authentication on both hops, including `/v1/cxone/*` and `/api/*`. Only sanitized `GET /healthz` liveness may be unauthenticated: return process liveness alone, no configuration, target, key, ledger, feature or failure details. Static local panel requests are authenticated or unavailable (404); there is no unauthenticated panel path around this rule. Browser users access Conductor, never receive either service key. The direct local panel cannot mutate in required mode without an approved server-side signer flow. Authentication applies to unknown paths too: only liveness is exempt.

Server forwards the compact assertion **unchanged**, never mints assertions/substitutes `requested_by`, replaces the hop-specific service credential, and passes status lookup requests and response status/metadata through unchanged. A hop failure never triggers a mutation retry. Bridge derives reviewer attribution from verified `iss` + `sub`; process `operator` remains separate. Synthetic keys only in tests. No key is provisioned by this proposal; startup loopback guard/no tunnel/no public panel policy remains. Off-host TLS is a requirement for any separately approved topology, not permission to expose Bridge or remove loopback enforcement.

## Transport and routing

`POST /v1/cxone/page/apply-fix` and `POST /v1/cxone/page/restore` receive one `reviewer_assertion` string in their JSON body, alongside `preview_token` and the existing compatibility `preview_hash`. No Authorization-header overload, URL parameter, cookie, multiple assertion fields, or camelCase alias. Assertion bytes must be printable ASCII, at most 8192 bytes, with exactly three nonempty unpadded base64url segments. Reject whitespace, padding, noncanonical base64url encodings, detached payloads, and additional segments. Do not log the assertion or include it in audit/snapshot metadata.

Preview and revise-preview responses add `review_binding` to their existing fields. Restore-preview adds canonical page identity and `review_binding`. This is additive on reads. Once the signed path is enabled by an approved rollout, missing assertions fail closed on **every HTTP mutation alias**, including `/api/apply`; tokenless mutation is rejected, never regenerated. The local panel must use an approved signer flow or be mutation-disabled in required-signature mode. CLI/operator workflows remain separately scoped local operations and must not provide an HTTP bypass. No automatic downgrade from required-signature mode.

## Signature and key selection

Use compact JWS, protected header exactly `{ "alg": "Ed25519", "kid": "<configured-id>", "typ": "remedy-review+jwt" }`. No additional header members, embedded `jwk`, `jku`, certificate URL, `crit`, `b64`, or unsigned header. Only raw Ed25519 signing/verification of the JWS signing input is permitted; reject `none`, HMAC, RSA, `EdDSA`, Ed448, and cross-algorithm key use. RFC 9864 defines the fully specified `Ed25519` JOSE identifier; this is a deliberate new contract, not silent acceptance of both algorithm names. The selected compatibility path is **native Node 22 `node:crypto`**: `sign(null, ASCII(signingInput), Ed25519PrivateKey)` and `verify(null, ASCII(signingInput), Ed25519PublicKey, raw64ByteSignature)`, with explicit protected-header `alg === "Ed25519"` validation. `null` here selects Ed25519's intrinsic signing behavior, not `alg:none`. Node crypto does not perform JOSE dispatch; the reviewed JWS wrapper must enforce the exact algorithm/header/encoding rules. The installed older Conductor `jose` dispatches `EdDSA` only and is **not** this path. No alias/fallback to `EdDSA`, no silent dependency upgrade. Product wrapper and its integration still need review/tests before landing; the offline corpus proves compatibility of these native primitives only.

`kid` matches `[A-Za-z0-9._-]{1,64}` and selects an exact entry in a locally provisioned keyring. Each entry pins issuer, audience, environment, trust epoch, `kty=OKP`, `crv=Ed25519`, public key, `not_before`, `not_after` (integer UTC seconds), `enabled` and nullable `revoked_at`. Require `not_before <= iat`, `exp <= not_after`, and `not_before <= verification_now < not_after`; issuer/audience/epoch must match the active configured deployment. Require enabled and no effective revocation (`revoked_at <= verification_now` rejects **all** assertions from that key, including ones issued before revocation). Recheck enabled/revocation/windows inside the durable pre-dispatch authorization step; revocation stops new dispatch, cannot undo an already dispatched write. Once effectively revoked, clock movement never re-enables the key: persist the revocation, and require a new kid for re-enablement. It is never a filename, network URL, or discovery input. Unknown/disabled IDs fail closed without fetching anything. Production must refuse the fixture ID and public fixture key used below.

Signing input is ASCII `base64url(UTF8(headerJSON)) + '.' + base64url(UTF8(payloadJSON))`; signature is 64 raw bytes, then unpadded base64url. Verify the **received encoded segments**, never parse then reserialize before verification. JSON object member order and JSON whitespace are not cryptographic canonicalization requirements: two valid JSON encodings are different signed byte strings and independently verifiable. Strictly decode and parse the **untrusted protected header before verification only to select an exact locally configured `kid` and enforce its fixed header policy**. Header parsing rejects duplicate decoded member names (including escaped aliases), unknown fields, invalid UTF-8/Unicode/surrogates and non-object forms; no header value is trusted as authorization. Decode the payload segment canonically as bytes but do not parse or read any payload field before successful signature verification. Then strictly parse the verified payload, rejecting duplicate decoded names at every depth, invalid Unicode/surrogates, arrays where objects are required, unknown/missing members or wrong types. JSON depth is at most 32; compact input is at most 8192 ASCII bytes. No BOM, leading/trailing bytes outside JSON whitespace, padding or non-zero unused base64url bits. Native `JSON.parse` alone is insufficient because it silently accepts duplicates. The fixture freezes exact JSON texts and bytes for cross-language verification. No JCS dependency or undocumented JSON key sorting is required.

## Exact payload

All fields below are required; no extra fields. `review_binding` itself is the object in the `binding` claim.

| Field | Type and rule |
|---|---|
| `v` | Integer `1`. |
| `iss` | Exact configured environment-specific issuer, e.g. `urn:libretexts:conductor:test`. |
| `aud` | One exact string for the receiving Bridge deployment, e.g. `urn:libretexts:remedy-bridge:test`; arrays forbidden. |
| `sub` | Verified immutable Conductor user ID, 1–128 visible ASCII characters (`0x21`–`0x7e`), no spaces/controls. Audit records `{issuer, subject}` without conflating it with operator. |
| `iat`, `nbf`, `exp` | Safe integer Unix seconds. `nbf == iat`, `0 < exp-iat <= 60`. At verification time `iat <= now+5`, `nbf <= now+5`, and `now < exp` (no expiry grace). `exp` cannot exceed Bridge preview expiry. |
| `jti` | Nonce: unpadded base64url of 32 cryptographically random bytes (43 chars). Unique for the issuer across all actions/targets. |
| `binding` | Exact object described below; equality is structural with exact primitive types/values, never coercion or normalized comparison. |

`binding` contains exactly these members:

| Field | Type and rule |
|---|---|
| `action` | `cxone.apply` or `cxone.restore`; fixed by route, never by caller mode alone. |
| `target` | Exactly `{hostname, page_id, page_path}`. Host is lowercase configured DNS host without trailing dot, port, scheme, or credentials. `page_id` is canonical positive decimal **string**, no leading zeros, within JS safe integer range. `page_path` is Bridge's canonical authoritatively resolved path. |
| `preview_token` | Exact opaque token Bridge issued; UUID-form currently, do not derive from content. Token must refer to an unexpired stored preview. |
| `before_sha256` | 64 lowercase hex SHA-256 of UTF-8 source HTML bytes used by the preview; no HTML normalization, truncation, or newline rewriting. |
| `after_sha256` | 64 lowercase hex SHA-256 of exact UTF-8 HTML bytes Bridge will submit to CXone; includes any byte-preserving patch result, computed **before review**. No later regeneration or unreviewed serialization. |
| `fix_mode` | `deterministic`, `pipeline`, or `restore`. Apply accepts first two; restore accepts only `restore`. |
| `tier` | Integer 1–3 for pipeline; `null` for deterministic/restore. |
| `snapshot` | `null` for apply; for restore exactly `{timestamp, sha256}`, where timestamp is exact selected metadata ISO string and hash is full SHA-256 of restored HTML bytes. |

The Bridge creates the target from authoritative `resolvePageRef` metadata, using the exact returned path in the stored binding. The writer separately checks the owner sandbox policy (currently `normalizeSandboxPath` rejects traversal, backslash and NUL forms); that predicate does not rewrite the path in this binding. Canonical preview output is authoritative: Conductor and Server **copy it unchanged**, never independently decode/re-encode its path. Before write, Bridge resolves input and numeric ID, checks their agreement and allowlist, compares the canonical target to the stored preview and signed claim, and submits only to that numeric ID. A page rename/move requires a fresh preview. Signing does not override owner allowlist, feature flag, stale-source check, or content policy.

The current `preview_hash` is a 16-hex compatibility hash (`guardrails.ts:hashContent`); it remains a UI compatibility field, **not** either full digest above. This proposal requires additive full digest fields rather than pretending that existing field is a SHA-256 commitment. Preview output must already be final wire HTML; if the writer changes bytes after review, the binding must fail before mutation.

## Durable ownership, claims and dispatch

This v1 supports **one Bridge writer process per store** on a supported local POSIX filesystem (Linux/macOS), not NFS, a shared network volume, replicas or an untested lock emulation. Proposed concrete store: SQLite with WAL, `synchronous=FULL`, foreign keys and transactional uniqueness; snapshots and the separate fence below are persistent storage. A second process must fail closed **before listening or advertising ready**:

1. Resolve the configured store/fence location to canonical paths. Acquire and retain a nonblocking OS exclusive `flock`-compatible lock on a stable owner-lock file for the process lifetime. Never unlink/replace that lock file, break locks by age, use an expiring lease, or continue after ownership is lost. The approved implementation needs a reviewed Node 22 compatible native lock adapter or local helper and actual two-process tests; this document does not claim such an adapter exists in the product. All deployments of the same store must share this lock path/inode. A copied store does not authorize a second writer for the same CXone targets; deployment preflight must reject multiple enabled writers. Multi-host ownership remains unsupported.
2. Open/validate the ledger under that lock and require active trust epoch equality with a separately provisioned current epoch/fence on a persistent mount **excluded from ledger backups and preserved across code rollback**. Every state transaction increments `durability_seq`. Commit SQLite FULL, then atomically replace the fence `{trust_epoch, durability_seq}` using file fsync + rename + directory fsync; only after both commits/flushes may a remote mutation start. On startup, any missing/corrupt fence, epoch mismatch or sequence mismatch disables writes and requires explicit local reconciliation. Crash between the two flushes fails closed, not implicit repair. No compatible filesystem durability/locking proof means no write readiness.
3. Ledger constraints: unique `(issuer,jti)` across all actions/targets/epochs; unique preview token claim; at most one active or quarantined operation per canonical `(hostname,page_id)`. Use a transaction and unique indexes, not a check followed by an independent insert. Token claims and nonce tombstones are never removed by routine cleanup in v1; terminal outcomes remain durable. Private HTML/assertion bytes/keys are not stored in claim rows. Store canonical binding digests/identity, action, subject+issuer, expiry, operation UUID, state, timestamps and snapshot/audit/revision references under the reviewed retention policy.
4. Authenticate the hop, strictly check assertion/schema/key/time, compare stored preview/binding and canonical target authorization. Consume the in-process token synchronously before the first awaited eligibility read. Before remote dispatch, atomically persist the durable token/nonce claim and reserve the target, then flush DB+fence. A rejected/failed claim never mutates CXone. If a lock/claim is already held, return conflict; do not queue a blind mutation retry. Re-resolve the target and re-read source under ownership, reject stale source, and recheck key/time/preview validity immediately before dispatch. A no-change result follows the no-op rule below.
5. Save/fsync the pre-write snapshot and metadata before mutation; any snapshot/ledger/disk-full failure **before** a durable dispatch marker means no remote call. Persist+flush `write_started` and its recovery references before sending exactly one remote request. Disable SDK/client/proxy mutation retries. While a response is pending the claim remains active. `write_started` found after crash is conservatively `unknown_write` and quarantined before writes can be re-enabled, even if the process died before actually sending.
6. Remote success received is `known_success` regardless of later append-audit failure. Persist+flush that outcome before acknowledging it; return `audit_recorded:false` when audit append fails. If remote success is observed but ledger/fence persistence fails, stop write admission globally; do not acknowledge an unrecorded terminal success or retry. A best-effort error may report `unknown_write` only if it is safe to respond; otherwise fail/close the request. Read-only status returns the last durable `pending` state until restart/recovery conservatively marks it unknown. Neither a 5xx nor status `pending` proves no mutation.
7. Transport loss/rejection after dispatch is conservatively `unknown_write`: retain consumed nonce/token and active-target quarantine, invalidate old evidence, and forbid subsequent mutations until an explicit audited local resolution. New previews may be generated but do not clear quarantine. Disk-full/outage after dispatch blocks all new writes; never convert an unpersisted attempt into available state. Status lookup is read-only and returns 503 if the ledger cannot be read safely.

**Backup/rollback policy is enforced fail-closed:** a ledger backup excludes the independent current epoch/fence; restoring an older DB produces a fence/sequence mismatch and disables writes. The supported restore procedure also sets write admission disabled **before** restoring any storage. Recovery either stays disabled until claims, pending attempts and target state are explicitly reconciled, or deliberately creates a new trust epoch **and new signing key IDs/keys**, revokes all old-epoch keys, invalidates all old previews, reconciles every unresolved target, and establishes matching new ledger/fence under exclusive ownership before explicitly enabling writes. Old nonce records/history are retained or archived read-only, never offered as new claims. A code rollback preserves ledger/fence/snapshots/audit and cannot disable required signatures. Rolling back both a ledger and its independent fence/config/keyring is unsupported and cannot be claimed detectable from the stale copy itself. Administrative bypass is outside the guarantee; no automated restore/upgrade may do it. The product, restore tooling and deployment bundle must prove these rules before release.

## Outcomes, no-op evidence and readonly operation lookup

Conductor durably stores `(issuer,jti)` **before submission**, tied to the verified user, project, canonical target, exact preview/binding and local operation record; it knows the nonce without receiving a Bridge `operation_id`. A lost response is resolved by lookup, never by resubmitting a mutation or creating another nonce to retry it. Conductor checks current user/project permission and its stored operation mapping on every lookup; browser-supplied `issuer`/`jti`/operation ID cannot select arbitrary records. Read-only auditor/foreign-project users cannot query mutation operations without the applicable project operation permission.

`POST /v1/cxone/page/operation-status` has exact JSON body `{ "issuer": "<configured issuer>", "jti": "<canonical 43-character nonce>" }`, no additional fields or reviewer assertion. Both hops authenticate as above; Server passes the exact pair and Bridge HTTP status/JSON metadata through unchanged and never regenerates an assertion. The Bridge queries its ledger by `(issuer,jti)` without CXone calls or claim creation; no mutation, audit repair, quarantine clear or remote retry occurs. Authentication failures are 401; Conductor mapping/permission failures 403; malformed query 400; unknown claim 404 `operation_not_found`; unreadable/untrusted ledger 503 `claim_store_unavailable`. A 404 during an in-flight/lost request is **not proof of no remote write** and never authorizes retry.

A known operation returns HTTP 200 with exactly this metadata, no HTML, raw assertion, service credential, reviewer display data, filesystem paths or signed claims:

```json
{"operation_id":"<stable Bridge UUID>","action":"cxone.apply","outcome":"pending",
 "reason":null,"applied":null,"restored":false,"audit_recorded":null,
 "requires_reconciliation":false,"reconciliation":"none","evidence_effect":"hold",
 "updated_at":"<UTC ISO timestamp>"}
```

`operation_id` is created once with the durable claim and remains stable. `reason` is `null` or a fixed code (`no_change`, `stale_preview`, `target_mismatch`, `pre_dispatch_failure`, `write_outcome_unknown`); never raw upstream error text. `reconciliation` is `none`, `required` or `resolved`. The inactive action boolean is always false. The active boolean is null until actual outcome is known; an unknown original mutation stays null even after local reconciliation. `audit_recorded` is null until a write's audit append result is known, then boolean. `updated_at` changes only on durable state events, never a poll. Status response shapes/states are versioned by this exact proposal.

| Durable outcome | Active boolean / audit | Evidence and caller behavior |
|---|---|---|
| `pending` | active `null`; audit `null`; target reserved. | `evidence_effect:hold`: freeze mutation confirmation/exports until terminal lookup. Do not infer success, failure or retry safety. |
| `not_attempted` | both false; audit null; reason fixed, including `no_change`. No remote mutation. | `evidence_effect:preserve` except `stale_preview`/`target_mismatch`, which invalidate. A **confirmed no-op** preserves existing evidence; it does not certify externally changed source or create new scan evidence. Tokens/nonces remain consumed. |
| `known_success` | active true; inactive false; audit boolean. | `evidence_effect:invalidate`, even when audit failed. Only a fresh actual scan can establish current evidence. |
| `unknown_write` | active null; inactive false; audit null unless durably known; reconciliation required. | `evidence_effect:invalidate`; never coerce null to false/no-op. Quarantine persists across restarts/new previews. |

Mutation responses use the same metadata schema plus errors as applicable: 200 for confirmed no-op or known success; 502 `write_outcome_unknown` for an unknown attempt, with `requires_reconciliation:true`. Include `operation_id` if durable claim exists. Eligibility rejections before a claim return `{error,outcome:"not_attempted",retryable:false,operation_id:null}` and have no status row. Invalid signature/key/schema/time/issuer/audience is 401, valid-signature binding/action mismatch 403, expired/stale/claimed preview or active target 409, claim-store failure before dispatch 503. No response echoes cryptographic internals. **Actual mutation**, **confirmed no mutation**, and **uncertain mutation** stay distinct in every consumer; generic `!applied` is not a sufficient decision. The LT-116 local HTTP fields/status (including unknown 409) remain unchanged until coordinated implementation of this approved future contract; no existing forwarding compatibility is claimed here.

Local reconciliation is an explicitly invoked **read-only** procedure: an authorized operator reads the ledger operation, saved snapshot/audit evidence and CXone contents/revision history through GET/read APIs, then saves a report identifying evidence, uncertainty and recommended disposition. It never POSTs/PUTs content, changes claim outcome, clears quarantine, rotates keys or enables writes. Status lookup cannot trigger it automatically. Any later administrative resolution must be a separately authorized local action which appends an auditable resolution event, keeps nonce/token consumed and original outcome immutable, and releases a target only after unresolved attempts are accounted for. `reconciliation:resolved`/`requires_reconciliation:false` reflect only such an explicit persisted resolution, never a poll, elapsed time, key rotation or a comparison heuristic. Rescan remains required after actual/unknown writes.

## Provisioning and rotation handoff

Proposed names (names only): Conductor `REMEDY_REVIEWER_SIGNING_KEY_FILE`, `REMEDY_REVIEWER_KEY_ID`, `REMEDY_REVIEWER_ISSUER`, `REMEDY_REVIEWER_AUDIENCE`; Bridge `REMEDY_REVIEWER_KEYRING_FILE`, `REMEDY_REVIEWER_REQUIRED`, `REMEDY_CLAIM_DB`, `REMEDY_CLAIM_FENCE_DIR`, `REMEDY_REVIEWER_TRUST_EPOCH`; Server and Bridge `REMEDY_BRIDGE_SERVICE_KEY_FILE`. Conductor copies the configured active trust epoch/key ID through its approved signer configuration, not browser input. Existing Conductor→Server `APP_API_KEY` stays on its hop only. Server receives no reviewer signing key. No secret in image, source, browser, logs, or fixture. File permissions, container UID, mounts and health/preflight are a separate reviewed deployment deliverable.

Rotation order: provision new public key alongside old at Bridge, validate readiness, switch Conductor signing to new ID, wait at least maximum assertion lifetime + skew + in-flight bound, then retire old key. Apply keyring changes through an explicit local reload that pauses new dispatch, validates and atomically installs the complete keyring, then acknowledges the new generation before admission resumes. An invalid/unreadable reload keeps writes disabled. Effective revocations are persisted before acknowledgment and consulted at pre-dispatch; merely editing a file is not an acknowledged revocation. Emergency disable rejects the old ID immediately upon that acknowledged installation, including previously issued unexpired assertions; already dispatched writes remain subject to outcome recovery. Required-signature startup fails when keyring/ledger/issuer/audience is absent, invalid or unwritable. Rollback never silently disables signature enforcement or restores an older consumed-claim ledger. Johnny performs real key provisioning and live coordination only after the code, full-stack synthetic test, deployment bundle, and exposure policy are approved.

## Fixture evidence and limits

Corpus identity: **`lt1-wire-v1-r2`** in `lt-1-reviewer-wire-v1-vectors.json`, frozen together with this document/generator/checker by one commit. Public deterministic test phrase derives forgeable fixture material, never a real credential. The JSON freezes exact encoded segments/bytes, full compact assertions, raw-signature validity, expected rejection stage and fixed context (clock, preview binding and key policy). There are 3 valid apply/restore/pipeline cases and 40 negative cases. Schema/time/audience/action/duplicate-header/payload/key/encoding negatives have **valid Ed25519 signatures over their exact received segments**; two separate cryptographic tamper cases are invalid. Duplicate names include escaped header aliases and nested payload duplicates. Other cases cover invalid UTF-8/surrogates, padding/noncanonical unused bits, key iat/exp/current windows and revocation. No JWS library algorithm fallback is used.

Commands (offline after obtaining the Node binary):

```sh
node docs/proposals/lt-1-reviewer-wire-v1-vectors.mjs
node docs/proposals/lt-1-reviewer-wire-v1-checks.mjs
# Actual compatibility check used a separately cached Node 22.22.0 executable:
npm exec --yes --package=node@22.22.0 -- node docs/proposals/lt-1-reviewer-wire-v1-checks.mjs
```
